# Web UI (Phase 20) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a zero-build, zero-new-dependency browser UI (plain HTML + JS + CSS served by the FastAPI app) that spectates running games live by polling the existing `/api/v1` routes, with a human-input drawer so the human player can act (`/actions`) and speak (`/input`). The DoD — "human player and agent NPCs develop a full adventure, not only kill a goblin" — is a **milestone** validated by a live end-to-end smoke test in the final task, not feature work in this plan.

**Architecture:** New `src/interfaces/web/` adapter (`CLAUDE.md` §63). One static HTML shell per page drives everything client-side from `fetch` calls to `/api/v1`. The server ships only static files; there is **no server-side templating** (jinja2 is not a dependency and stays out). CLI, API, and Web share the same composition root and application services — the Web layer contains zero game logic (§40). The API contract is frozen: this plan must not add or change any endpoint (grill answer #7).

**Spec:** `docs/architecture/domain-model-and-api.md` (partially; see the `spec-gap` note in the contract task below).

**Roadmap:** `docs/superpowers/plans/README.md` row following the Phase 19 Web API plan.

**Existing API surface (verified, frozen for this plan):**

| Route | Notes |
|---|---|
| `POST /api/v1/games` | body `{campaign_name, seed?}`; `Idempotency-Key` header; returns `SessionResponse{game_id, view, opening}` (201) |
| `GET /api/v1/games/{id}` | `GameViewResponse` — party, enemies, combat |
| `GET /api/v1/games/{id}/status` | `StatusResponse` — status, combat, game_over |
| `GET /api/v1/games/{id}/events` | full list, `{"events": [EventEnvelopeResponse…]}` with monotonically increasing `sequence` |
| `POST /api/v1/games/{id}/actions` | `{action_type, target?, weapon_id?}`; target accepts id or case-insensitive name; drains pending agent turns first; returns `TurnReportResponse` |
| `POST /api/v1/games/{id}/input` | `{text}`; routes via `session.play.apply_input` (attack verb / say / etc.); returns `InputResponse{kind, report?, gm?}` |

Known event types: `GameCreated, GameStarted, InitiativeRolled, CombatStarted, TurnStarted, TurnEnded, AttackRequested, AttackResolved, DamageApplied, CharacterDefeated, ActionRejected, CombatEnded`.

## Global Constraints

- **Interface layer only**: all new source lives under `src/interfaces/web/` plus at most a one-line `create_app` wiring change if needed for serving. Verify `git diff --stat HEAD -- src/domain src/application src/interfaces/api` is empty in the final task (no API changes).
- **No new dependencies**: plain JS/CSS/HTML only. `StaticFiles` is built into FastAPI; no jinja2, no Node/npm, no HTMX (plain JS suffices for a poll-based spectator).
- **No game logic in JS**: JavaScript only renders server-computed state and forwards user input. Dice, damage, legality, and resolution stay on the server (`CLAUDE.md` §1, §40).
- **UI adapts to the API, not vice versa** (grill answer #7): any desired data that `/api/v1` does not expose is out of scope and recorded as a Phase 21 candidate.
- **No secrets**: env keys resolved by `session.factory` as today; never referenced by the web layer.
- **Deterministic tests**: all route tests run with fake sessions and keys blanked (`OPENROUTER_API_KEY= OPENCODE_API_KEY=`). No live LLM calls anywhere in CI. The live GLM smoke test in the final task is manual (runbook below), not CI.
- **Type/lint gates** — always `set -o pipefail` first:

```bash
set -o pipefail
V=$PWD/.venv/bin/python
$V -m pytest tests/interfaces/web -q | tail -1
$V -m ruff check .
$V -m mypy | tail -1
OPENROUTER_API_KEY= OPENCODE_API_KEY= $V -m pytest -q | tail -1
```

- **Commits**: conventional, scoped (`feat(interfaces-web): …`), ending with `Co-Authored-By: Claude Code <noreply@anthropic.com>`.

## File Structure

| File | Responsibility |
|---|---|
| `src/interfaces/web/__init__.py` | package docstring |
| `src/interfaces/web/mount.py` | `mount_web(app: FastAPI) -> FastAPI` — mounts `static/` at `/` and routes `GET /` → `index.html`, `GET /games/{game_id}` → `game.html` |
| `src/interfaces/web/static/index.html` | lobby shell |
| `src/interfaces/web/static/game.html` | game shell |
| `src/interfaces/web/static/app.js` | lobby + game logic: new game, polling loop, rendering, drawer submit |
| `src/interfaces/web/static/style.css` | minimal styles |
| `tests/interfaces/web/test_mount.py` | mount/route tests (offline) |
| `tests/interfaces/web/app_test_helpers.py` | module-scoped fake app shared by the route tests below |

Note: `app.js` grows across tasks; JavaScript has no type/lint gate, keep functions small and imperative, no frameworks, no build step.

- [ ] Tests: `GET /` returns 200 HTML; `GET /games/x` returns 200 HTML; static `app.js` served.

### Task 2 — Lobby (`index.html` + start of `app.js`)

- [ ] New-game form: campaign name (default "The Forgotten Ruins"), seed (optional integer). Submit → `POST /api/v1/games` with `Idempotency-Key = crypto.randomUUID()`; on 201 redirect to `/games/{game_id}`.
- [ ] Render `SessionResponse.opening` GM narration as a lead-in line on the game page after creation (store `game_id` in `sessionStorage`; lobby passes it via redirect URL, not localStorage).
- [ ] Submission disable + error surface (`message`, status code) on failure; never echo request headers.
- [ ] No list-of-running-games feature: the registry is per-process in-memory state with no listing endpoint, and the frozen contract forbids adding one. A "return to an existing game" path is out of scope (Phase 21 candidate).

### Task 3 — Game shell + polling loop (`game.html`, `app.js`)

- [ ] Parse `game_id` from the URL path (`/games/{id}`).
- [ ] Poll on a single 2.5 s `setInterval`, driven by a single guard against overlapping in-flight requests: first `GET /status`; if `game_over`, stop the timer.
- [ ] Then `GET /events` and append to the feed only envelopes with `sequence > lastSeq`, newest on top; persist `lastSeq` for the session. (The endpoint currently returns the full list — client-side filtering is the no-API-change answer; do not ask the backend for `since=.`)
- [ ] Event feed line rendering per type (feed formatting task ref: task 5 table).
- [ ] Rerenderable DOM: party panel, enemies panel, combat tracker containers; a `render(view)` function owns them fully (idempotent re-render on each poll).

### Task 4 — Panels: party roster, enemies, combat tracker

- [ ] Party roster row per `CharacterResponse`: name, class/level, HP bar (`hp_current/hp_max`), AC, conditions tags, defeated styling (`is_defeated`).
- [ ] Enemies panel rows: same fields, no roster emphasis.
- [ ] Combat tracker: `round_number`, `status`, initiative order list, active actor highlighted (compare `active_actor_id`); absent when `combat: null` (outside combat → hide tracker, show status line).
- [ ] All rendering from server fields only — no derived rules math in JS (e.g. no "bloodied" inference; render only `hp_current <= 0` via `is_defeated`).

### Task 5 — Event feed formatting

- [ ] Map by `event_type` to one readable line using payload fields only; keep a stable display-name table in `app.js`:

| event_type | line shape (from payload) |
|---|---|
| `AttackResolved` | attacker names, hit/miss, damage in `payload` fields as available — inspect `AttackResolved`/`DamageApplied` payloads first, then write the formatter (payloads live in `src/domain/events/events.py`) |
| `DamageApplied` | amount + target |
| `CharacterDefeated` | target down |
| `ActionRejected` | reason (visible and honest — §28) |
| `CombatStarted/Ended`, `InitiativeRolled`, `TurnStarted/Ended` | terse, or skipped for `TurnStarted/Ended` if noisy (decide live) |
| unknown type | `— {event_type}` + compact JSON line (never lie by omission) |

- [ ] Test formatting as pure functions decoupled from the DOM (extract to small helpers so they are unit-testable without a browser; keep them in `app.js` — no build step).

### Task 6 — Human input drawer

- [ ] Drawer on the game page, collapsed by default: two lanes.
- [ ] **Speak lane:** textarea → `POST /input` `{text}` with `Idempotency-Key`; on response, render `kind` + `gm.narration`/`gm.npc_reply` (if any) in a GM strip above the feed; surface `error_code`/`reason` from `report` on rejection.
- [ ] **Act lane:** attack form — `action_type` fixed `attack` (top), target `<select>` populated from the latest view (`party + enemies`, `$name ($hp)`), optional free-text weapon id. Submit → `POST /actions` with `Idempotency-Key`; render `accepted`/`error_code`/`reason`; on `accepted` the poller picks up the resulting events and view naturally.
- [ ] The act lane mirrors CLI ergonomics (CLI-style target resolution happens server-side in `resolve_target`) — no client-side target validation beyond having a select list.
- [ ] Disable drawer while a submit is in flight; idempotency keys are per-submit, never reused.
